> [!NOTE]
> Supabase Auth emails (signup confirmation, password reset, magic link, change email) are managed independently in the Supabase Dashboard and use the custom HTML layouts in `docs/email-templates/`. All other operational emails generated by the application itself are governed by this document.

## 2. Local Previewing & Adding New Templates

### Generating Local Previews
To preview all emails in your browser without sending real emails or configuring API keys:

```bash
npm run email:preview
```

This runs `scripts/preview-emails.mjs`, which:
1. Renders all templates with realistic bilingual sample data (testing novel titles, order numbers, and Urdu Nastaliq typography).
2. Verifies PII redaction by testing raw IBANs and 12-digit TIDs to ensure `[REDACTED_ACCOUNT]` and `[REDACTED_NUMERIC_ID]` masks are applied.
3. Writes individual standalone `.html` and `.txt` files to `.preview/emails/`.
4. Generates an interactive visual gallery at `.preview/emails/index.html` with responsive desktop (560px) and mobile (375px) iframe previewers and search filters.

### Steps to Add a New Template
1. **Define Template in Database Migration**:
   - If critical (must bypass marketing opt-outs), add to `v_is_critical` list in `public.enqueue_email_for_notification` in a new sequential migration.
2. **Register in `src/lib/email/templates.ts`**:
   - Add entry to `TEMPLATE_REGISTRY` with:
     - `badgeText` & `badgeUrdu`
     - `ctaLabel` & `ctaPath` (must resolve to an existing App Router route in `src/app/`)
     - `whatHappenedEn` & `whatHappenedUr`
     - `actionGuidanceEn` & `actionGuidanceUr`
3. **Add Sample Fixture in `scripts/preview-emails.mjs`**:
   - Add realistic sample data to `SAMPLE_FIXTURES`.
4. **Run Verification Gates**:
   ```bash
   npm run email:preview
   npm run check:links
   npm run check:terms
   npm test
   ```

## 3. Email Outbox Architecture & 429 Quota Protection

UNB Premium utilizes an append-only transactional outbox pattern to decouple database writes from third-party email provider latencies and outages.

```
[Application / RPC]
        │
        ▼ (enqueue_email_for_notification)
[public.email_outbox] ◄─── State: pending, claimed_at, attempts, retry_after
        │
        ▼ (POST /api/cron/send-emails)
[src/lib/email/dispatch-outbox.ts]
        │
        ├─► Lease Locking: claim_email_outbox_batch (FOR UPDATE OF eo SKIP LOCKED)
        ├─► Inter-message delay (550ms pacing)
        │
        ▼ (src/lib/email/mailer.ts)
[Email Provider: Resend / Brevo]
```

### Lease Locking (`0051_email_outbox_lease_and_quota_retry.sql`)
- To prevent duplicate sends from concurrent cron runs, workers invoke `claim_email_outbox_batch(p_batch_size, p_lease_seconds)`.
- Rows are locked using PostgreSQL `FOR UPDATE OF eo SKIP LOCKED` and stamped with `claimed_at = now()`.
- If a worker crashes mid-send, the lease expires after 300 seconds, allowing a subsequent worker to safely retry.

### Rate Limits & Quota Protection
- **Resend**: Free and standard tiers enforce a strict rate limit of **2 requests per second**.
  - `dispatch-outbox.ts` includes an active **550ms pacing delay** between consecutive sends.
  - Upon receiving an HTTP 429 response, the dispatcher inspects `Retry-After`, stamps `retry_after = now() + interval '...'`, and trips an in-memory circuit breaker to halt the batch immediately.
- **Brevo**: Enforces a daily sending quota (300 emails/day on free tier).
  - When Brevo returns a quota error, `mailer.ts` classifies it as `daily_quota`, and `dispatch-outbox.ts` marks the message to retry after midnight UTC, preventing futile retry loops and log exhaustion.

### PII Sanitization Invariant
Platform emails **never** transmit sensitive payment data. The `sanitizeEmailContent` function automatically scans all dynamic text:
- Pakistani IBANs (`PK...`) are replaced with `[REDACTED_ACCOUNT]`.
- Long numeric sequences ($\ge 9$ digits) are replaced with `[REDACTED_NUMERIC_ID]`.
- Supabase storage URLs pointing to payment proofs are replaced with `[SECURE_PORTAL_PROOF_LINK]`.

## 4. Production DNS Configuration Guide for the Domain Owner

To guarantee inbox delivery to Gmail, Yahoo, and Outlook without being marked as spam or rejected, configure your domain's DNS records as follows:

### 1. SPF (Sender Policy Framework) — CRITICAL RULE
> [!CAUTION]
> **NEVER CREATE A SECOND SPF RECORD!**
> RFC 7208 strictly states that a domain must have **exactly one** TXT record beginning with `v=spf1`. If your DNS already has an SPF record (e.g. for Google Workspace or Hostinger), publishing a second SPF record will result in a permanent **SPF PermError**, causing emails to be rejected by major providers.

**How to Merge SPF Correctly:**
- **Existing record example**:
  ```text
  v=spf1 include:_spf.google.com ~all
  ```
- **If using Resend**:
  Merge `include:resend.com` into the existing record:
  ```text
  v=spf1 include:_spf.google.com include:resend.com ~all
  ```
- **If using Brevo**:
  Merge `include:spf.sendinblue.com` into the existing record:
  ```text
  v=spf1 include:_spf.google.com include:spf.sendinblue.com ~all
  ```

### 2. DKIM (DomainKeys Identified Mail)
- Add the exact DKIM CNAME or TXT records specified in your Resend or Brevo dashboard for `urdunovelbanks.com`.
- DKIM signatures cryptographically prove that the email was sent by UNB Premium and has not been altered in transit.

### 3. DMARC (Domain-based Message Authentication)
Publish a DMARC TXT record on your root domain to monitor and protect brand reputation:
- **Host**: `_dmarc.urdunovelbanks.com`
- **Type**: `TXT`
- **Recommended Initial Value (Monitoring Mode)**:
  ```text
  v=DMARC1; p=none; rua=mailto:dmarc-reports@urdunovelbanks.com; sp=none;
  ```
- Once aggregate reports show 100% DKIM and SPF alignment across Resend/Brevo, update policy to quarantine:
  ```text
  v=DMARC1; p=quarantine; rua=mailto:dmarc-reports@urdunovelbanks.com;
  ```

### 4. Custom Return-Path / Mail-From Domain
Configure a custom return-path subdomain (e.g. `bounces.urdunovelbanks.com` or `mail.urdunovelbanks.com`) following the provider dashboard instructions. This ensures SPF aligns with the RFC5321.MailFrom domain, satisfying DMARC alignment criteria.

## 5. Production Cron Dispatch Automation

In production, email sending and scheduled reminders are driven by two secured HTTP endpoints:

### 1. Email Outbox Dispatch (`/api/cron/send-emails`)
- **Schedule**: Every minute (`* * * * *`).
- **Endpoint**: `POST https://premium.urdunovelbanks.com/api/cron/send-emails`
- **Authentication**: Header `Authorization: Bearer <CRON_SECRET>`
- **Behavior**:
  - Claims up to 25 pending or retryable emails via `claim_email_outbox_batch`.
  - Dispatches each email via configured provider (`resend` or `brevo`).
  - Records success or updates attempts/backoff on failures.
  - Returns JSON summary: `{ success: true, processed: 12, sent: 12, failed: 0 }`.

### 2. Automated Reminders (`/api/cron/reminders`)
- **Schedule**: Hourly (`0 * * * *`).
- **Endpoint**: `POST https://premium.urdunovelbanks.com/api/cron/reminders`
- **Authentication**: Header `Authorization: Bearer <CRON_SECRET>`
- **Behavior**:
  - Invokes `check_verification_reminders()` RPC.
  - Enqueues 12-hour and 24-hour verification reminders for writers with unverified orders.
  - Enqueues tip reminders and automatically expires unconfirmed tips older than 7 days.
  - Returns JSON summary: `{ success: true, enqueued_reminders: 3 }`.
